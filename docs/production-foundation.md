# Production Foundation

## Identity And Access

The current runnable foundation uses HMAC-signed JWTs issued by `auth-service` and validated by each service as a Spring Security resource server through `JWT_SECRET`. Access tokens are short-lived (15 minutes by default), use the stable user id as `sub`, and include issuer, audience, token id, issue/expiry timestamps, email, role/roles, and scope claims. Every HTTP service validates signature, expiry, issuer, and audience.

Production should replace the shared HMAC secret with an OAuth2/OIDC provider that publishes a JWKS endpoint. Acceptable providers include a managed IAM provider such as Okta, Auth0, Microsoft Entra ID, AWS Cognito, or an internally operated Keycloak deployment. Tokens must include:

- stable user id claim
- tenant or facility claim
- role and scope claims
- session or token id for revocation and incident response
- assurance/MFA context where required

The production IAM migration sequence is:

1. Select the provider and register separate API audiences and operator/client applications.
2. Publish issuer and JWKS metadata, then overlap old and new validation during a controlled key migration.
3. Replace the HMAC decoder beans with issuer/JWKS validation; no service may retrieve or share a signing private key.
4. Map provider groups/scopes to application authorities and add tenant, facility, patient, consent, and break-glass policy checks.
5. Enable MFA, refresh-token rotation, revocation/session controls, lockout, recovery, and authentication audit events at the provider.
6. Remove `JWT_SECRET` from application tasks after every caller has migrated and the old token lifetime has elapsed.

## Authorization Baseline

All HTTP services now require bearer-token authentication by default. Public unauthenticated paths are limited to:

- auth-service `/login` and `/validate`
- actuator `health` and `info`

OpenAPI and Prometheus endpoints require the `ADMIN` role by default. Local Compose explicitly opts into public access with `PUBLIC_API_DOCS_ENABLED=true` and `PUBLIC_METRICS_ENABLED=true` so development tooling can scrape and aggregate documentation. Controller-level role gates are in place as coarse service policies. Patient-level, facility-level, consent, and break-glass checks remain the next authorization layer.

The gateway validates tokens locally and forwards the original bearer token. It no longer calls auth-service once per protected request, removing auth-service availability from the request path while preserving service-level validation downstream.

## Secrets

Local development reads secrets from the ignored `.env` file, with `.env.example` containing placeholders only. Applications have no built-in signing-key fallback and fail fast when `JWT_SECRET` is absent. The CDK stack models the JWT signing key as an AWS Secrets Manager secret and injects it into ECS tasks. Database credentials are generated by RDS secrets.

Production deployments should not commit secrets, bake secrets into container images, or pass long-lived secrets as plain text in IaC.

## TLS And mTLS

Ingress TLS terminates at the managed load balancer or API gateway using an ACM-managed certificate. HTTP is redirected to HTTPS, modern TLS policies are enforced, and only the public gateway security group accepts internet traffic.

Internal HTTP, gRPC, Kafka, and database traffic moves to private subnets. Service identity is provided by a service mesh or sidecar/workload-identity mechanism that issues short-lived certificates from a private CA. Both peers verify SAN-based workload identity; hostname-only or shared client certificates are not accepted. Certificates rotate automatically before expiry, trust-bundle rotation supports an overlap window, and revocation/rotation failures alert operations.

Rollout order: gateway ingress TLS, database/Kafka TLS, gRPC billing mTLS, then remaining service-to-service HTTP mTLS. Each stage requires automated handshake tests, plaintext-denial tests, certificate-expiry alerts, and a documented emergency rotation/rollback procedure before production promotion.

The interim local Compose setup is plaintext for developer ergonomics. It is not a production transport-security model.

## Observability

Each service exposes Spring Boot Actuator health and Prometheus metrics. Micrometer/OpenTelemetry tracing is enabled and log patterns include application name plus trace/span ids. Local Compose includes Prometheus, alert rules, Grafana datasource provisioning, and a service overview dashboard. The trace exporter/backend is deployment-specific; production must configure one before release.

Production observability should ship structured JSON logs, distributed traces, metrics, dashboards, and alerts to the selected platform. PHI must be excluded from logs, metrics labels, and trace attributes.

## Database Migration And Integration-Test Baseline

Auth, patient, billing, appointment, EHR, notification, and audit schemas are owned by Flyway and Hibernate runs in `validate` mode. Production migration locations contain schema only. Synthetic local seed data is isolated in `db/dev-migration` and enabled explicitly by Compose, preventing known development accounts or patients from being inserted by production deployments.

The integration-test module uses Testcontainers PostgreSQL to apply all seven production migration sets and verifies the expected tables are created without development rows. Live gateway workflow tests remain opt-in through `-DrunLiveIntegrationTests=true`.
