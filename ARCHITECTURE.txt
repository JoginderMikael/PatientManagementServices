PATIENT MANAGEMENT SERVICES - CURRENT ARCHITECTURE
==================================================

Last verified: 2026-09-10

SYSTEM SHAPE
------------

The repository is a Spring Boot microservice system behind one reactive API
gateway, with a React patient/staff frontend. Each domain service owns its own
PostgreSQL database. Kafka carries versioned integration events. The browser
uses only gateway routes and never connects directly to a service database.

External entry points:

  Frontend:    http://localhost:8085
  API gateway: http://localhost:4004
  Auth:        /auth/**
  APIs:        /api/**

The gateway and every backend resource service validate the JWT signature,
issuer, audience, expiry, and role. Backend method authorization is the actual
security boundary; frontend route policies are presentation controls only.


SERVICE OWNERSHIP
-----------------

auth-service
  Owns credentials, auth user UUIDs, roles, and account status. Account states
  are INVITED, ACTIVE, LOCKED, and DISABLED. Only ACTIVE users can log in.
  ADMIN can create users and change roles/status through /auth/admin/users.

patient-service
  Owns the master patient index, MRN, demographics, external identifiers,
  duplicate handling, merge history, and patient lifecycle. ADMIN, CLINICIAN,
  and REGISTRATION_STAFF can currently register patients. Patient changes and
  their outbox events commit in one local transaction.

patient-portal-service
  Owns patient portal activity, owner identity mappings, proxy grants, record
  releases, and portal payments. portal_identity explicitly maps an auth JWT
  subject to a patient-service UUID. A mapping has its own status and a cached
  patient lifecycle status.

billing-service
  Owns billing accounts, invoices, postings, and revenue workflows. It consumes
  PATIENT_REGISTERED idempotently to create a billing account.

appointment-service
  Owns schedules, appointments, waitlists, virtual consultation references, and
  appointment consent forms.

ehr-service
  Owns encounters, histories, diagnoses, prescriptions, laboratory results,
  notes, vaccinations, and clinical safety workflows.

insurance-service
  Owns policies, eligibility evidence, claims, adjudication, remittance, and
  billing reconciliation.

inventory-pharmacy-service
  Owns inventory, batches, movements, prescriptions, safety review, dispensing,
  and medication billing coordination.

notification-service
  Owns queued notification messages and delivery-oriented workflows.

staff-dashboard-service
  Owns operational rounds, patient chart summaries, staff tasks, handoffs,
  comments, escalation, and work queues.

audit-compliance-service
  Owns immutable audit projections, privacy consent, emergency access,
  independent review, compliance cases, holds, and retention workflows.

analytics-service
  Owns aggregate analytics/report definitions and consumes patient events for
  operational analytics processing.


IDENTITY MODEL
--------------

authUserId and patientId are deliberately different identifiers:

  JWT sub (authUserId)
          |
          v
  patient-portal-service.portal_identity
          |
          v
  patient-service patientId

Equal UUID values must never be assumed to establish the relationship. The
mapping is explicit and is the server-side authorization source of truth.

Current secure access flow:

1. auth-service authenticates an ACTIVE account and issues a JWT whose subject
   is authUserId.
2. The patient frontend calls GET /api/portal/me without supplying patientId.
3. patient-portal-service resolves the ACTIVE portal_identity for JWT sub.
4. Ownership requires both portal status ACTIVE and cached patient status ACTIVE.
5. Patient lifecycle events suspend access when the patient becomes INACTIVE,
   MERGED, or ARCHIVED and restore eligibility on a valid ACTIVE projection.
6. If there is no valid mapping, /portal/me returns 409
   PORTAL_ENROLLMENT_REQUIRED.

ADMIN may create a mapping through POST /api/portal/identities. Before insertion,
patient-portal-service forwards the administrator JWT to verify both sides:

- auth-service user exists, has role PATIENT, and has status ACTIVE;
- patient-service patient exists and has status ACTIVE.

The old GET /api/portal/patients/{patientId}/overview route remains for
administrator support only. PATIENT clients must use /api/portal/me.


USER AND PATIENT CREATION
-------------------------

Clinical patient registration and login-account creation are separate by design.
Registering a patient does not silently issue credentials. The current operator
flow is:

1. Create the clinical patient with POST /api/patients.
2. Create an ACTIVE PATIENT auth account with POST /auth/admin/users.
3. Bind auth user ID to patient ID with POST /api/portal/identities.
4. The binding service validates both records and activates portal ownership.

The immediate-password admin API is the currently implemented operational
foundation. Invitation tokens, contact verification, MFA enrollment, and a
durable multi-step enrollment saga remain required before real patient use.

Workforce users are created only by ADMIN through the same auth administration
API. Role and status changes are also ADMIN-only. Direct database insertion is
not an application workflow.


CONSISTENCY MODEL
-----------------

There is no distributed database transaction. The system uses local
transactions, a patient transactional outbox, versioned Kafka events, and
idempotent consumers.

Guaranteed locally:

- patient row and patient outbox event commit together;
- patient registration retries can use Idempotency-Key;
- patient email and MRN constraints protect the patient database;
- billing creates at most one account per patient;
- portal ownership requires a unique auth subject and unique patient ID;
- a newly created portal binding is validated against auth and patient services.

Eventually consistent:

- billing account provisioning;
- audit projections;
- analytics event processing;
- patient lifecycle projection in patient-portal-service.

Still requiring future work:

- invitation/activation and MFA workflows;
- immediate revocation or auth lifecycle-event propagation for already-issued
  access tokens (current access tokens expire after their configured short TTL);
- a durable enrollment saga with visible PENDING/FAILED states;
- dead-letter/replay tooling and automated reconciliation dashboards;
- consistent patient existence checks in every patient-referencing service;
- complete merge/archive propagation policies for all downstream records; and
- patient-safe demographic/clinical profile projection through the portal.
